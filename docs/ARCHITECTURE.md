# Architecture

The Python package owns investigation state and LangGraph orchestration. The Go service provides synthetic incident health, metrics, and log observations over local HTTP plus one loopback-only mock action with an in-memory receipt ledger. Python has an injected loopback-only client for that action; the graph calls it only on the opt-in simulated route after a checkpointed approval. Later, an MCP adapter will expose diagnostics to the graph. No production infrastructure is connected.

Current flow: `START -> receive_incident -> classify -> severity_policy -> END` by default. An explicit `retrieval_mode = "history"` routes through `retrieve_history` before classification when a retriever is injected. An explicit `classification_mode = "llm"` routes through `llm_classify` before policy when a model is injected. An explicit `investigation_mode = "simulated"` routes after policy through a deterministic plan, one diagnostic read, evidence evaluation, and a bounded loop before diagnosis. The investigated path defaults to deterministic diagnosis. `diagnosis_mode = "llm"` requires an injected diagnosis model and selects a separate bounded model node after `finish_investigation`. Intake validates the report and initializes counters. The caller supplies a `thread_id` so `InMemorySaver` can checkpoint execution.

`IncidentReport` records the incoming facts. `InvestigationState` carries classification and policy results, historical matches, diagnostic checks and counters, current evidence, fixed failure categories, a stop reason, and diagnosis source/failure/call accounting. Each evidence item records its incident, service, source kind, stable ID, source reference, observation time, and bounded observation. Historical matches and tool failures are stored separately and cannot become current evidence. The optional OpenAI classifier and diagnoser adapters are injected independently; the default path remains local and needs no API key or embedding model.

Target flow: `incident input -> optional historical retrieval -> baseline and/or LLM classification -> investigation plan -> diagnostic tools -> evidence evaluation -> conditional loop -> diagnosis -> human approval -> simulated remediation -> verification -> report`.

`graph.py` owns topology, conditional edges, cycle bounds, and checkpoint compilation. `nodes/` owns one decision or effect per node. `schemas.py` owns graph state and separate classifier and diagnoser output contracts, which are validated before entering state. `tools/` owns external clients. The Go service supplies simulated observations; an MCP adapter may expose those same diagnostic capabilities later. A historical incident match carries similarity and provenance, but is never evidence that the current incident has the same cause.

Phase 4 uses a validated fixture store and `GET /incidents/{id}/health`, `/metrics`, and `/logs` on the loopback Go service. Process `/health` remains independent. The Python diagnostic client restricts requests to those three reads on a loopback HTTP origin and validates each response. The opt-in graph checks health, metrics, and logs in that order, retries only transient failures once, and stops after at most three rounds or six actual client attempts. Empty data and failures yield no evidence. After every simulated investigation stop, the graph checkpoints a validated diagnosis. The deterministic rule supports the original `diag-db-auth` login rejection through current health and log evidence. The model route accepts a supported finding only after citation validation and this same narrow mechanism policy; it otherwise abstains or falls back. The alternate `diag-db-auth-alt` fixture is a held-out wording challenge. Neither route explains why authentication was rejected. The default classification-only route has no diagnosis. Phase 6 has a checkpointed approval interrupt and a separate execution node on the explicit `remediation_mode="simulated"` route. It revalidates the proposal and decision, checks the local ledger, then sends at most one action request. An applied receipt leads to a fresh incident health read. Only a healthy `db_login_restored` check with a valid post-action time yields `verified`; other reads produce failed or unknown verification. A separate report node summarizes every terminal Phase 6 route while preserving diagnosis and severity. Phase 7 replaces process-local checkpointing for restart safety. No multi-agent layer is planned. See [PHASE5_IMPLEMENTATION.md](PHASE5_IMPLEMENTATION.md) for contracts and evaluation.
