# Mock service

Requires Go 1.22 or newer. Run `make run` and request `curl http://127.0.0.1:8080/health`. The process health endpoint returns `{"status":"ok"}`. Use `SENTINEL_MOCK_SERVICE_PORT` to change the port. The server binds to `127.0.0.1` only. Run `go test ./...` for fixture and HTTP contract tests.

The three Phase 4 diagnostic reads are `GET /incidents/{id}/health`, `GET /incidents/{id}/metrics`, and `GET /incidents/{id}/logs`. For example, `curl http://127.0.0.1:8080/incidents/diag-degraded/health` returns a fixed synthetic observation with `incident_id`, `service`, `observed_at`, `status`, and bounded `checks` (`id`, `status`, `detail`). `curl http://127.0.0.1:8080/incidents/diag-degraded/metrics` returns a matching snapshot with bounded numeric metrics (`id`, `name`, `value`, `unit`, `window`). A window such as `5m` is a duration string. `curl 'http://127.0.0.1:8080/incidents/diag-degraded/logs?limit=2'` returns up to two fixed log entries with stable IDs, timestamps, components, levels, and messages. Logs default to 20 entries and allow at most 50; invalid limits return 400 with `{"error":"invalid_limit"}`.

The fixture IDs are `diag-healthy`, `diag-degraded`, `diag-db-auth`, `diag-db-auth-alt`, `diag-missing`, and `diag-unhealthy`. `diag-db-auth` has explicit synthetic database login rejection observations in health and logs, plus a connection-failure metric. `diag-db-auth-alt` is a separate Phase 5 challenge fixture with the same observed failure mechanism expressed through different IDs and wording. `diag-missing` returns `unknown` health with no checks and empty metrics and logs lists. Empty metrics or logs means no observation, not a measured zero. Unknown IDs return 404 with `{"error":"incident_not_found"}`; invalid IDs return 400 with `{"error":"invalid_incident_id"}`. Go's `GET` route pattern also accepts HEAD; POST remains rejected on diagnostic read routes.

Fixtures contain observations only, with no cause or severity labels. Python's opt-in graph can read them and produce a cited diagnosis. The incident metrics are fixed fixtures; this service does not run Prometheus or expose process instrumentation at `/metrics`.

## Phase 6 local mock action

The service also accepts `POST /incidents/diag-db-auth/remediations` for the single allowlisted `restore_simulated_db_login` action. The JSON body must name a bounded `action_id`, the matching incident and `api` service, `action`, `proposal_id`, a 64-character lowercase hexadecimal `proposal_fingerprint`, and the complete recorded `approval` (`decision_id`, proposal ID and fingerprint, incident ID, service, `decision: "approve"`, operator ID, and RFC 3339 decision time). The handler rejects unknown fields, trailing JSON, oversized bodies, missing or mismatched approval, other incidents, and other actions with fixed JSON error codes. The service validates the approval record's shape and binding; it does not authenticate the operator. Keep it on loopback and use no real infrastructure credentials.

A new accepted action returns `201` with an `applied` receipt. Repeating the same action ID and identical body returns the original receipt with `200`; changing the body for that ID returns `409 action_id_conflict`. Reusing an approval with another action ID returns `409 approval_already_used`. `GET /incidents/{id}/remediations/{action_id}` reads a receipt without repeating the effect. Unknown receipt IDs return `404 action_not_found`.

The action overlays only `diag-db-auth` incident health with a new `db_login_restored` check and an observation time equal to the receipt's `applied_at`. The embedded health, metrics, and log fixtures stay unchanged; a fresh service process starts from them. Process `GET /health` is independent of the incident overlay. Python has a validated action client, but the graph does not call this endpoint yet; Task 6 adds the guarded execution path. Run `go test -count=1 ./...` and `go test -race -count=1 ./...` for the store, HTTP, and concurrency contracts.
